ActiveRecord Scopes

Reference entry · last updated October 9, 2026

ActiveRecord scopes are named, reusable database queries defined on Rails models. A scope normally returns an ActiveRecord::Relation, allowing further query methods and scopes to be chained.[1]

This entry describes Rails 8.1. Examples are illustrative and assume a Post model with published, created_at, author_id and id columns, plus an Author model with has_many :posts. Unless stated, no default scope is present.

First principles and definitions

A relation holds query conditions. Building it with methods such as where and order normally defers fetching rows. to_a loads records; to_sql returns the SQL representation. A Rails console can load a relation when displaying it.[2][3]

query = Post.where(published: true).order(:id)
query.to_sql  # SQL for inspection
query.to_a    # load matching Post records

Defining scopes

scope takes a name and a callable body. A lambda runs when the scope is called, so time expressions inside it are evaluated on each call. Parameters become lambda arguments.[1]

class Post < ApplicationRecord
  scope :published, -> { where(published: true) }
  scope :since, ->(time) { where("created_at >= ?", time) }
  scope :recent, -> { since(1.week.ago) }
end

Post.published.recent

Placeholder values avoid interpolating input into SQL text.[4]

Scopes and class methods

A class method returning a relation can serve the same purpose. A scope body returning nil or false falls back to all in the current scope. A class method returns its ordinary Ruby result; nil breaks further chaining. none explicitly returns a chainable relation with no records.[1][4]

class Post < ApplicationRecord
  def self.since(time)
    time ? where("created_at >= ?", time) : all
  end

  scope :by_author, ->(id) { id ? where(author_id: id) : none }
end

The class method above is an alternative to the earlier since scope. by_author(nil) deliberately matches nothing.

Combining scopes

Chained where conditions combine with SQL AND. Explicit and and or combine relations from the same model that differ only in where, or in having when grouped.[2][4]

Post.published.where(author_id: 7)
Post.where(author_id: 7).or(Post.where(author_id: 9))

merge imports another relation's conditions. Overlapping conditions from the supplied relation take precedence; and expresses intersection. merge can also import conditions for a joined association.[5]

Post.where(published: true).merge(Post.where(published: false))
# published = false

Author.joins(:posts).merge(Post.published)
# authors joined to published posts

order appends ordering terms; reorder replaces them.[4]

Post.order(:created_at).order(:id)   # created_at, then id
Post.order(:created_at).reorder(:id) # id only

Associations

Model scopes and relation-returning class methods are available through collection associations. author.posts.published keeps the association's author condition while adding the publication filter.[1][2]

Default scopes

default_scope adds implicit query conditions and can supply attributes when building records. Multiple default scopes combine. Ordinary instance updates and deletes do not apply the default scope; all_queries: true extends its where conditions to those operations. Ordering is excluded from that extension.[6]

# Separate example: published becomes the implicit filter.
class Post < ApplicationRecord
  default_scope { where(published: true) }
end

# Alternative declaration, including instance updates/deletes:
# default_scope -> { where(published: true) }, all_queries: true

Removing conditions

unscoped removes previous scoping, including default and association conditions. author.posts.unscoped can therefore return posts belonging to other authors.[6]

unscope(:order) removes ordering; unscope(where: :published) targets an attribute condition. rewhere replaces specified conditions. Unlike except, unscope persists across merges.[4]

Post.published.unscope(where: :published)
Post.published.rewhere(published: false)

Creation defaults and pitfalls

Hash equality conditions can supply attributes to new and create.[3] SQL fragments do not supply those defaults.[2] create_with sets creation attributes explicitly.[4]

Post.published.new.published                   # true
Post.where("published = ?", true).new.published # column default
Post.create_with(published: true).new.published # true

Returning an array or a single record from a scope body loses relation composition. A conditional scope's nil fallback adds no restriction, so none is required when missing input must produce an empty result.[1][4]
